MediCore Development Guide

1. Purpose

This document describes how to develop, test, debug, and contribute to MediCore locally.

The repository contains two applications:

backend/
fronted/

The backend and frontend are developed independently but communicate over HTTP.

2. Prerequisites

Install:

Required

Git

Python 3.10

Node.js compatible with the frontend configuration

npm

PostgreSQL for production-like development, or use the default SQLite database

Docker, if testing container deployment

External accounts required for full AI functionality

Supabase

Pinecone

Groq

3. Clone the Repository

git clone https://github.com/vaddivenkatarambabu/Medical-chat-bot-AI.git
cd Medical-chat-bot-AI

4. Backend Setup

cd backend

Create a Python virtual environment:

Windows PowerShell

python -m venv .venv
.venv\Scripts\Activate.ps1

Linux/macOS

python3.10 -m venv .venv
source .venv/bin/activate

Upgrade pip:

python -m pip install --upgrade pip

Install runtime dependencies:

pip install -r requirements.txt

Install development dependencies:

pip install -r requirements-dev.txt

5. Backend Environment

Copy:

backend/.env.example

to:

backend/.env

Configure the required values.

At minimum, full RAG functionality requires:

PINECONE_API_KEY=
GROQ_API_KEY=

For Supabase authentication:

SUPABASE_URL=
SUPABASE_PUBLISHABLE_KEY=
SUPABASE_JWT_SECRET=

For production-style PostgreSQL:

DATABASE_URL=

6. Local Database

If DATABASE_URL is not configured, the backend automatically uses:

instance/medicore.sqlite3

The application can automatically create the SQLite schema.

This behavior is intended for local development.

Production PostgreSQL should use Alembic migrations.

7. Database Migrations

The project uses Alembic.

Typical commands:

alembic upgrade head

Create a new migration after model changes:

alembic revision --autogenerate -m "describe schema change"

Review generated migrations before applying them.

Do not blindly accept autogenerated migration output.

8. Running the Backend

From:

backend/

run:

python app.py

Default development address:

http://127.0.0.1:1819

Verify:

http://127.0.0.1:1819/health

Expected:

{
  "status": "ok"
}

9. Running with Gunicorn

For a production-like local test:

gunicorn --bind 0.0.0.0:1819 --workers 1 --timeout 120 app:app

10. Backend RAG Initialization

The RAG chain is lazy-loaded.

The first request that requires RAG may be slower because the process may need to initialize:

Hugging Face embeddings

Pinecone vector store

retriever

Groq client

LangChain chain

Subsequent requests reuse the cached chain within that process.

11. Building the Pinecone Index

The indexing script is:

backend/store_index.py

Run:

python store_index.py

The script reads PDFs from:

PDF_DATA_DIR

Default:

data

Current repository source:

backend/data/Gale Encyclopedia of Medicine Vol. 1 (A-B).pdf

12. Frontend Setup

Open another terminal.

cd fronted

Install dependencies:

npm install

The repository also contains a bun.lock file, but the Render configuration currently uses npm.

For consistent CI/deployment behavior, prefer npm unless the package-manager strategy is intentionally changed.

13. Frontend Environment

Copy:

fronted/.env.example

to:

fronted/.env

Vite will display the local development URL.

VITE_BACKEND_URL

srvx

22. Backend API Smoke Test

Health:

curl http://127.0.0.1:1819/health

curl -X POST http://127.0.0.1:1819/get \
  -H "Content-Type: application/json" \
  -d "{\"message\":\"What are common symptoms of dehydration?\"}"

The response is plain text.

23. Frontend Chat Flow

The frontend has a server-side route:

fronted/src/routes/api/chat.ts

This route:

Accepts the frontend chat request.

Reads the Authorization header.

Reads the guest session header.

Normalizes the request payload.

Calls backend /get.

Returns the backend response.

It is a proxy rather than an independent AI implementation.

24. Authentication Development Flow

The frontend uses Supabase JS.

The basic flow is:

Browser
   │
   ▼
Supabase Auth
   │
   ▼
Access token
   │
   ▼
Frontend API request
   │
   ▼
Authorization: Bearer <token>
   │
   ▼
Flask
   │
   ▼
Supabase token verification

The backend then synchronizes the external user into its local database.

25. Guest Development Flow

When there is no authenticated Supabase session:

Frontend
   │
   ▼
nanoid()
   │
   ▼
localStorage
   │
   ▼
medicore_guest_session_id
   │
   ▼
X-Guest-Session-Id

Guest users can therefore maintain conversations without creating an authenticated account.

26. Debugging Checklist

When the frontend cannot connect:

[ ] Is backend running?
[ ] Is VITE_BACKEND_URL correct?
[ ] Is backend CORS configured?
[ ] Is browser calling expected endpoint?

When authentication fails:

[ ] Supabase URL correct?
[ ] Supabase publishable key correct?
[ ] Backend JWT configuration correct?
[ ] User email verified?
[ ] Browser session still valid?

When RAG fails:

[ ] PINECONE_API_KEY set?
[ ] Pinecone index exists?
[ ] Index dimension = 384?
[ ] Correct embedding model?
[ ] GROQ_API_KEY set?
[ ] Groq model name valid?

When database operations fail:

[ ] DATABASE_URL correct?
[ ] PostgreSQL reachable?
[ ] Alembic migrations applied?
[ ] Database user has required privileges?

27. Recommended Development Workflow

Before changing code:

git status

Create a branch:

git checkout -b feature/<short-description>

Make focused changes.

Run:

git diff --check

Then run relevant tests and quality checks.

Review:

git diff
git status

Stage only intended files.

Commit using a conventional message.

Example:

git add backend/src/prompt.py
git commit -m "feat: improve medical response safety guidance"

Push:

git push origin feature/<short-description>

Open a pull request.

28. Commit Message Convention

Recommended prefixes:

feat:
fix:
docs:
refactor:
test:
ci:
build:
chore:
security:

Examples:

feat: add conversation history support
fix: validate guest conversation ownership
docs: document RAG deployment workflow
test: add chat persistence coverage
ci: add backend dependency audit
security: restrict authentication redirects

Commits should describe the change, not the person making it.

30. Medical-Specific Development Rules

Changes affecting the medical assistant should be reviewed more carefully than ordinary UI changes.

Avoid:

unsupported medical claims

fabricated citations

fabricated clinical evidence

deterministic diagnosis language

personalized medication dosing

unsafe treatment instructions

Changes to:

backend/src/prompt.py
backend/store_index.py
embedding configuration
retrieval configuration
LLM model configuration

should include appropriate regression testing.

31. Current Testing Gaps

Not currently implemented: dedicated frontend automated testing.

Recommended:

Vitest
React Testing Library

Recommended frontend coverage:

authentication states

chat submission

API errors

guest sessions

conversation CRUD

message rendering

route behavior

Not currently implemented: automated end-to-end browser testing.

Recommended:

Playwright

for critical user flows.

32. Current API Testing Gap

The backend has meaningful tests, but there is no verified generated API contract.

Not currently implemented:

OpenAPI specification

schema-generated API tests

client contract tests

These become increasingly valuable as the frontend/backend contract grows.

33. Current Knowledge-Base Testing Gap

The current RAG pipeline does not have a formal evaluation suite.

Not currently implemented:

retrieval recall benchmarks

groundedness tests

citation correctness tests

medical-answer regression set

prompt-injection evaluation

adversarial question suite

These should be added before large-scale production deployment.

34. Code Ownership Principle

The codebase should maintain clear responsibilities:

app.py
    HTTP orchestration

schemas.py
    request validation

auth.py
    authentication identity

repositories.py
    persistence operations

database.py
    database lifecycle

prompt.py
    LLM safety/instruction layer

helper.py
    document loading, splitting, embeddings

store_index.py
    offline knowledge-base ingestion

fronted/src/lib/
    frontend integration/auth/API state

fronted/src/routes/
    frontend routes/server handlers

Avoid moving database queries into route handlers when repository methods are appropriate.

Avoid putting provider-specific secrets or infrastructure logic into React components.

35. Local Development Principle

Local development should reproduce production architecture where practical:

Frontend
   ↓
Backend
   ↓
PostgreSQL / SQLite
   ↓
Pinecone
   ↓
Groq

However, SQLite remains useful for fast backend development and tests.

Production-specific behavior should be tested separately using PostgreSQL and containerized deployment.

36. Files That Should Not Be Committed

Never commit:

.env
.env.local
.env.production

or secrets such as:

PINECONE_API_KEY
GROQ_API_KEY
SUPABASE_JWT_SECRET
SUPABASE_SERVICE_ROLE_KEY
DATABASE_URL

Commit:

.env.example

with placeholder values only.
